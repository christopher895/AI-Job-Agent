# Watched GitHub Repos — Design

## Problem

Christopher wants to be notified when new rows are added to community-maintained
internship-tracking GitHub repos (starting with
[`vanshb03/Summer2027-Internships`](https://github.com/vanshb03/Summer2027-Internships)),
the same way he's already notified when the scraper detects new jobs on a company's
career page. He can't get a real-time webhook — he doesn't own the repo, and GitHub
only allows webhooks to be registered by repo admins — so this is a polling problem,
not a push problem.

## Key discovery

`vanshb03/Summer2027-Internships` (and other repos in this family, e.g. the
SimplifyJobs-style internship lists) publish a structured JSON feed at
`.github/scripts/listings.json` alongside their README, generated by the same
bot that renders the markdown table. Each entry looks like:

```json
{
  "id": "df70fa57-977b-4f31-832e-a0e57ed070b5",
  "company_name": "Rippling",
  "title": "Frontend Software Engineer Intern",
  "locations": ["New York, NY", "San Francisco, CA"],
  "url": "https://ats.rippling.com/en-GB/rippling/jobs/3fd9615a-...",
  "active": true,
  "is_visible": true,
  "season": "Winter",
  "date_posted": 1749260792
}
```

This is far more reliable than parsing the rendered README table, which uses `↳`
continuation rows for multi-role companies, `<details>` blocks for multi-location
rows, and emoji suffixes for sponsorship/citizenship/closed flags. Fetching the JSON
feed sidesteps all of that.

## Scope decisions (confirmed with Christopher)

- **Polling cadence:** piggyback on the existing 15-minute scraper cron tick. No
  dedicated faster poll, no webhook — true "instant" isn't possible here anyway.
- **Which repos:** a general "watched GitHub repos" list, editable via
  Preferences, seeded with `vanshb03/Summer2027-Internships`. Not hardcoded to
  one repo.
- **Filtering:** watched-repo jobs bypass the existing title/keyword/location
  preference filters entirely (`matchesLocation`, `scoreJob`,
  `applyPreferences`). Everything the feed marks `active: true` gets emailed,
  regardless of role (PM/quant/cyber included) or location.
- **Email:** watched-repo jobs go out in their **own** email, separate from the
  company-career-page digest, so they don't compete for the shared
  `maxPerEmail` slots.
- **Cap:** no cap. Every job newly detected since the last poll is emailed. The
  15-minute diff window naturally keeps most emails small; a large batch push to
  the repo just means a larger (but still accurate) email that cycle.

## Architecture

### New adapter: `scraper/adapters/github-repo.ts`

Same shape as the existing adapters (`scrapeGreenhouse`, `scrapeAshby`, etc.):

```ts
export async function scrapeGithubRepo(repoUrl: string): Promise<JobListing[]>
```

1. Parse `owner/repo` out of the given URL (accepts `https://github.com/owner/repo`
   or `owner/repo` shorthand).
2. `GET https://api.github.com/repos/{owner}/{repo}/contents/.github/scripts/listings.json`
   — the Contents API resolves the repo's default branch automatically, so no
   branch needs to be hardcoded or looked up separately. Response content is
   base64-encoded; decode and `JSON.parse`.
3. Filter entries to `active === true && is_visible !== false` (`is_visible`
   is a distinct "should this be shown" flag from `active`; treat a missing
   field as visible).
4. Map each entry to the existing `JobListing` shape:
   - `title` ← `title`
   - `company` ← `company_name`
   - `location` ← `locations.join(", ")`
   - `url` ← `url`
5. On any failure (404, malformed JSON, network error, rate limit) — log a
   warning naming the repo and return `[]` for this cycle. Never throws; the
   caller treats a failed repo the same as a company with zero current jobs
   (nothing new detected), and retries next tick.

No changes to the `JobListing` type. The feed's `id` field is not surfaced —
diffing reuses the existing `hashJob(url)` mechanism (the listing's `url` is
its direct ATS application link, unique and stable per posting).

### Storage: reuse `companies` + `snapshots`, no new tables

Each watched repo is registered as a row in the existing `companies` table via
`getOrCreateCompany(name, careersUrl, scrapeType)`:

- `name`: `owner/repo` (e.g. `vanshb03/Summer2027-Internships`)
- `careers_url`: the repo URL
- `scrape_type`: `'github-repo'`

Snapshot diffing reuses `getLatestSnapshot` / `saveSnapshot` / `diffSnapshots`
exactly as the company pipeline does today — no schema changes.

### New orchestration: `scraper/github-repos.ts`

Kept in its own file rather than growing `scraper/index.ts` further:

```ts
export async function runWatchedRepoScrapes(): Promise<void>
```

For each `url` in `preferences.watchedRepos`:
1. `getOrCreateCompany` for this repo.
2. `scrapeGithubRepo(url)` → current jobs (no location/keyword filtering
   applied here — that's the point).
3. Diff against the last snapshot (`hashJob(url)` per job, same as the
   company pipeline).
4. Collect newly-detected jobs; save the new snapshot regardless of whether
   anything new was found.

After processing all watched repos, if any new jobs were found across any of
them, send **one** combined email via the existing `sendJobEmail(jobs, source)`
helper (unchanged — it already takes an arbitrary `source` label), with
`source` describing the watched repo(s), e.g. `vanshb03/Summer2027-Internships`
or `2 watched GitHub repos` when there's more than one.

### Cron integration

`cron/scheduler.ts` calls `runWatchedRepoScrapes()` alongside
`runAllCompanyScrapes()` on the same 15-minute tick (both wrapped so one
failing doesn't block the other — matches the existing
`Promise.allSettled` failure-tolerance pattern used per-company).

## Preferences changes

- `agent/src/config.ts`: `Preferences.watchedRepos: string[]`, default
  `["https://github.com/vanshb03/Summer2027-Internships"]` in `FILTERS`.
- `agent/src/api/routes/preferences.ts`: PUT validation extended to require
  `Array.isArray(body.watchedRepos)`.
- `web/lib/api.ts`: mirror `watchedRepos: string[]` on the web-side
  `Preferences` type.
- `web/components/PreferencesForm.tsx`: new "Watched GitHub Repos" section
  using the existing `TagInput` component (same pattern already used for
  `priorityCompanies`), with helper copy explaining it polls on the normal
  15-minute cycle and emails separately from the main job digest.

## Error handling summary

| Failure | Behavior |
|---|---|
| Malformed/unparseable repo URL in prefs | Log warning, skip that entry, don't crash the tick |
| Repo has no `.github/scripts/listings.json` (404) | Log warning naming the repo, return no jobs, retry next tick |
| `listings.json` exists but isn't a JSON array (unexpected shape) | Log warning naming the repo, return no jobs, retry next tick |
| GitHub API rate limit hit | Log warning, return no jobs, retry next tick |
| One watched repo throws | Doesn't block other watched repos or the company scrape pipeline |

GitHub's unauthenticated rate limit (60 req/hr per IP) is a non-issue at one
request per watched repo per 15-minute tick for a small list. If Christopher
watches many more repos later, an optional `GITHUB_TOKEN` env var could raise
this to 5000/hr — not needed for this initial scope (one repo).

## Testing

- Unit test for the `listings.json` → `JobListing` mapping/filtering logic
  (given a fixture JSON blob, assert `active: false` entries are dropped and
  fields map correctly), following the existing pattern in
  `scraper/test-fixtures/`. No live network calls in tests.

## Out of scope

- True real-time push notification (not possible without owning the repo).
- Parsing the rendered README table (superseded by the `listings.json` feed).
- Season filtering (`Summer` vs `Fall`/`Winter`/`Spring`) — not requested;
  `active` is the only filter applied.
- Deduping/merging a watched-repo job against a job already seen via the
  direct company-page scrape (out of scope for this iteration; a job could
  theoretically be emailed twice via two different sources).
